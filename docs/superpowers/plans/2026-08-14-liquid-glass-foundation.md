# Liquid Glass Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add three glass constructors to `OakUIConstructionFunctions`, with a working test target, so later increments adopt `NSGlassEffectView` through one correct seam rather than 12 independent guesses.

**Architecture:** Extend `Frameworks/OakAppKit/src/OakUIConstructionFunctions` — an existing shared seam imported by 46 files. The constructors encode two things every call site would otherwise have to rediscover: that `NSGlassEffectView` hosts content through its `contentView` property rather than by adding subviews, and that adjacent glass surfaces must share an `NSGlassEffectContainerView` or they seam visibly. Creating `OakAppKit_test` is a prerequisite, not scope creep: the framework has no test target today, so there is no way to test the constructors otherwise.

**Tech Stack:** Objective-C++, AppKit (macOS 26.5 SDK), XcodeGen (`project.yml`), the home-grown CxxTest-style runner generated by `Xcode/scripts/gen_test.sh`.

**Spec:** `docs/superpowers/specs/2026-08-14-liquid-glass-design.md`

## Global Constraints

- **Deployment target is macOS 26.0.** Never write `@available(macOS 26, *)` guards or `NSVisualEffectView` fallbacks — every branch would be dead code. Third-party examples (iTerm2's included) carry such guards; do not copy them.
- **arm64 only.** Do not add x86_64 fallbacks.
- **Build with `bin/build`, never bare `xcodebuild`.** It sanitises leaked `GEM_HOME`/`GEM_PATH` from Ruby version managers, which otherwise break the Ruby build phases with a misleading `Symbol not found: _rb_cArray`.
- **Never run `bin/deploy-local`.** The maintainer runs the signed Homebrew build; deploy-local installs an ad-hoc build that cannot self-update.
- **Tests live at `Frameworks/<name>/tests/t_*.{cc,mm}`** and contain top-level `void test_*()` functions using `OAK_ASSERT`, `OAK_ASSERT_EQ`, `OAK_ASSERT_NE`. The older `class X : public CxxTest::TestSuite` files in `Frameworks/OakAppKit/tests/` are inert leftovers — `gen_test.sh` does not glob them. Do not imitate or fix them.
- **This increment is additive and ships nothing user-visible.** No `CHANGELOG.md` entry, therefore no release. Pushing `CHANGELOG.md` to master is what triggers a release; leave it alone.

### Task 3: `OakCreateGlassBackground`

The constructor that matters most. `NSGlassEffectView` hosts content through its `contentView` property — adding subviews directly does not work — and callers need an optional tint.

**Files:**
- Modify: `Frameworks/OakAppKit/src/OakUIConstructionFunctions.h`
- Modify: `Frameworks/OakAppKit/src/OakUIConstructionFunctions.mm`
- Test: `Frameworks/OakAppKit/tests/t_glass.mm`

**Interfaces:**
- Consumes: nothing from Task 2 (independent).
- Produces: `NSGlassEffectView* OakCreateGlassBackground (NSGlassEffectViewStyle style, NSColor* tint);`

- [ ] **Step 1: Write the failing tests**

Append to `Frameworks/OakAppKit/tests/t_glass.mm`:

```objc
void test_glass_background_applies_style ()
{
	NSGlassEffectView* regular = OakCreateGlassBackground(NSGlassEffectViewStyleRegular, nil);
	OAK_ASSERT(regular != nil);
	OAK_ASSERT_EQ(regular.style, NSGlassEffectViewStyleRegular);

	NSGlassEffectView* clear = OakCreateGlassBackground(NSGlassEffectViewStyleClear, nil);
	OAK_ASSERT_EQ(clear.style, NSGlassEffectViewStyleClear);
}

void test_glass_background_nil_tint_leaves_system_default ()
{
	NSGlassEffectView* view = OakCreateGlassBackground(NSGlassEffectViewStyleRegular, nil);
	OAK_ASSERT(view.tintColor == nil);
}

void test_glass_background_applies_tint_when_given ()
{
	NSColor* tint = [NSColor colorWithWhite:0.5 alpha:0.5];
	NSGlassEffectView* view = OakCreateGlassBackground(NSGlassEffectViewStyleRegular, tint);
	OAK_ASSERT(view.tintColor != nil);
}

void test_glass_background_hosts_content_via_contentView ()
{
	// The API contract callers get wrong: content goes in contentView, not as a
	// subview. Encoding it here means one place to be right instead of twelve.
	NSGlassEffectView* view = OakCreateGlassBackground(NSGlassEffectViewStyleRegular, nil);
	NSView* content = [[NSView alloc] initWithFrame:NSZeroRect];
	view.contentView = content;
	OAK_ASSERT_EQ(view.contentView, content);
}
```

- [ ] **Step 2: Run the tests to verify they fail**

Run: `bin/build OakAppKit/test`
Expected: FAIL to compile — `use of undeclared identifier 'OakCreateGlassBackground'`

- [ ] **Step 3: Declare it in the header**

Append to `Frameworks/OakAppKit/src/OakUIConstructionFunctions.h`:

```objc
// `style` is NSGlassEffectViewStyleRegular for chrome sitting over content, or
// NSGlassEffectViewStyleClear for transient overlays that should read through.
// `tint` may be nil for the system default; when non-nil it must be a dynamic
// colour that resolves for both light and dark appearance.
//
// Put content in the returned view's `contentView`. Adding subviews directly
// does not composite correctly.
NSGlassEffectView* OakCreateGlassBackground (NSGlassEffectViewStyle style, NSColor* tint = nil);
```

- [ ] **Step 4: Implement it**

Append to `Frameworks/OakAppKit/src/OakUIConstructionFunctions.mm`:

```objc
NSGlassEffectView* OakCreateGlassBackground (NSGlassEffectViewStyle style, NSColor* tint)
{
	NSGlassEffectView* res = [[NSGlassEffectView alloc] initWithFrame:NSZeroRect];
	res.translatesAutoresizingMaskIntoConstraints = NO;
	res.style = style;
	if(tint)
		res.tintColor = tint;
	return res;
}
```

- [ ] **Step 5: Run the tests to verify they pass**

Run: `bin/build OakAppKit/test`
Expected: PASS, all six tests so far.

- [ ] **Step 6: Commit**

```bash

Encodes the contentView contract in one place: NSGlassEffectView hosts content
```

## What this plan deliberately does not cover

Increments 2 through 6 from the spec — small controls, overlays, chrome bars, choosers and window chrome, and the tab bar — are **not planned here**.

The spec's own rationale is that increments 2 and 3 exist to *learn* how glass behaves against TextMate's layout: whether `NSGlassEffectView` fights manual frame arithmetic, how `contentView` hosting interacts with existing constraints, and what tint each surface actually needs. Writing bite-sized steps for those now would mean inventing those answers, and a plan whose steps look confident but rest on guesses is worse than no plan.

Each adoption increment gets planned after the foundation exists and after its target file has been read, with screenshots in both appearances reviewed before the next begins.
