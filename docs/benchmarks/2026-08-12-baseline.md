# Baseline — 2026-08-12

Measured on macOS 26.6.1, Xcode 26.6, Apple Silicon.

Method: `bin/bench/baseline.sh`. Launch time is measured to first successful
Apple Event reply, which requires the main run loop to be running — a real
"ready to use" signal rather than a proxy for it. Both releases are signed
with a Developer ID and notarized, so both were launched under Gatekeeper's
normal accepted path (see `task-4-report.md` for the full `spctl`/`codesign`
output). Two independent full runs of `bin/bench/baseline.sh` produced
consistent results (launch: 847ms/699ms official, 724ms/661ms undead; RSS:
130MB/130MB official, 141MB/141MB undead); the table below is the more
recent of the two.

| build | size KB | archs | rpath dylibs | launch ms | RSS MB |
|---|---|---|---|---|---|
| official | 38496 | x86_64+arm64 | 0 | 699 | 130 |
| undead | 27928 | arm64 | 0 | 661 | 141 |

`official` = TextMate v2.0.23 (`textmate/textmate`, released 2021-10-12).
`undead` = TextMate v2.1.4-undead (`textmatelives/textmate`, released
2026-06-11). Both are Universal/current releases as published; `official`
is the last release of the pre-fork lineage, `undead` is the most recent
community-maintained release and is the baseline Phase 3 and Phase 7 are
measured against, per the plan.

## Measurement limits, stated honestly

- Launch time includes Gatekeeper's first-run verification on the very first
  launch. All recorded numbers are from the *second* launch onward.
- Large-file open time is not automated. It is measured manually against a
  generated 100 MB file and recorded separately.
- RSS is sampled once after the window appears, not at steady state.
- **rpath dylib count is 0 for both builds, and this is a real, verified
  reading, not a measurement gap.** Neither shipped `.app` contains any
  `.framework` or `.dylib` payload at all (`Contents/Frameworks/` does not
  exist in either bundle) — `otool -L` on the main executable shows only
  absolute-path system frameworks (`/System/Library/...`, `/usr/lib/...`)
  for both. The ~45 modules under this repository's source-tree
  `Frameworks/` directory (48 subdirectories, confirmed by listing) are
  therefore already fully statically linked into each shipped Mach-O by the
  current build, in both the 2021 and 2026 lineages. Phase 7's target of
  "measurable improvement over `undead` on... rpath dylib count" cannot be
  read against *this* baseline as written — the metric is pinned at zero
  for the current architecture. Whoever scopes Phase 7 in detail should
  re-anchor that claim, e.g. to Mach-O/executable file count across the
  bundle, or to build-time linkage of the source tree's `Frameworks/`
  modules, rather than expect this baseline's rpath count to move.
- The `undead` on-disk size above (27928 KB / 27.3 MB, via `du -sk` on the
  expanded `.app`) is larger than the "roughly 11.4 MB" figure in the task
  brief. That figure matches the *compressed download asset*
  (`TextMate-2.1.4-undead.tbz`, 12,016,708 bytes = 11.46 MiB), not the
  installed bundle footprint. Both numbers are real; they measure different
  things. This baseline uses installed on-disk size throughout, since that
  is what Phase 2's Intel-stripping and Phase 7's static-linking work
  actually change, and what a user has on disk day to day.
- Automation (TCC) permission for controlling the launched app by bundle ID
  was available in this measurement session, so launch time and RSS were
  both measured directly for both builds — neither is a "not measured"
  case here. `bin/bench/measure.sh` still treats an unavailable/blocked
  Automation permission as a first-class outcome: each `osascript` call is
  bounded (2-3s per call, ~30s for the responsiveness poll) and reports
  `not measured (timeout)` for launch and RSS rather than hanging or
  fabricating a number, so a future run without this permission granted
  degrades honestly instead of failing the whole harness.

## Targets these numbers set

- Phase 3 must not regress size or launch versus `undead`.
- Phase 7 must show measurable improvement over `undead` on launch, size,
  and rpath dylib count. The dylib count is the direct proxy for the
  45-framework static-linking work. (See the caveat above: this baseline's
  rpath count is 0 for both builds, so this specific claim needs
  re-scoping before Phase 7 can be judged against it.)
