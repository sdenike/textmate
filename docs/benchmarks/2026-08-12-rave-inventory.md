# rave build inventory — 2026-08-12

Generated by `bin/rave2yaml --inventory` (Phase 2 Task 1). This is the checklist Task 7
verifies Xcode-project parity against, and the source data Task 4 converts into
`project.yml`. Regenerate with:

```
./bin/rave2yaml --inventory
```

## Method

`bin/rave2yaml` walks `Frameworks/*/default.rave` and `Applications/*/default.rave` (56
files) plus `vendor/*/default.rave` (3 files, reported separately — see below), parsing
the directive grammar implemented by `bin/rave`'s `Parser` class (`load_recursive`,
`flatten`, `expand_globs`, `create_targets`) rather than inferring it from samples.
Unlike `bin/rave` itself — which warns to STDERR and continues on a directive it doesn't
handle (`create_targets`'s `else` branch) — `rave2yaml` treats any unrecognised directive
as fatal: file, line, and directive name. A silently-dropped directive is how a converted
build ends up subtly wrong, which is worse than the tool refusing to run.

**Directive grammar found in `bin/rave`** (block-openers, then per-line commands):

| Directive | Kind | In this tree? | Notes |
|---|---|---|---|
| `target "name" { }` | block | yes (57×) | Opens a target. Name is usually `${dirname}`, but not always — see Surprises. |
| `config "name" { }` | block | yes (2×, one file) | Config-scoped overrides (debug/release). Only `TextMate` uses it, only for `PLIST_FLAGS`. |
| `load` | top-level | root only | Recursively pulls in other `.rave` files. Only appears in the repo-root `default.rave`; never inside a per-target file. Not implemented — would error loudly if seen. |
| `extend` | block | no | Extends an existing target from elsewhere. Not implemented. |
| `arch "name" { }` | block | no | Architecture-scoped overrides. Not implemented. |
| `notarize` | line | no | Notarization credentials. Not implemented. |
| `define` | line | no | Custom named build action. Not implemented. |
| `prelude` | line (glob) | root only | Precompiled header source. Global in root `default.rave`; never per-target here. |
| `require` | line (list) | yes (50×) | Strong dependency: pulls in the target's objects, headers, frameworks, libraries. |
| `require_headers` | line (list) | yes (4×) | Weak dependency: headers only, no linking. |
| `headers` | line (glob, dir-relative) | yes (46×) | Exported headers — the mechanism behind `ExportHeader` (369 edges per prior recon; the load-bearing risk for Task 3). |
| `sources` | line (glob, dir-relative) | yes (57×) | Compiled source files. |
| `tests` | line (glob, dir-relative) | yes (26×) | Test sources wired into the `gen_test`/`RunTest` pipeline (`<target>/test`). |
| `cxx_tests` | line (glob, dir-relative) | yes (3×: `ns`, `layout`, `OakAppKit`) | Parsed and glob-expanded by `bin/rave`, but **no code in `bin/rave` ever reads `target[:cxx_tests]`** — there is no `Target.cxx_tests` and no ninja rule consumes it. All three uses are named `gui_*.mm`. This looks like GUI tests deliberately kept out of the automated (headless-capable) `tests/*` pattern, existing today as declarative-only metadata. Task 4 needs to decide whether to preserve, manually wire, or drop these. |
| `frameworks` | line (list) | yes (33×) | macOS frameworks to link. |
| `libraries` | line (list) | yes (4×) | Libraries to link (`-lname`, or a `.a` path). |
| `executable` | line (scalar) | yes (11×, 10 files) | Marks the target as producing a Mach-O executable; presence is what this inventory's `kind` classification keys off. |
| `prefix` | line (scalar) | yes (4×) | Bundle-relative install path (`*.app/Contents`, `*.xpc/Contents`, `*.qlgenerator/Contents`). Absence + `executable` present = plain command-line tool. |
| `set` / `add` / `capture` / `expand` | line | yes | Variable plumbing (assign / append / shell-capture / file-expand-and-assign). Recognised so real content doesn't trip the unrecognised-directive error, but **verified by grep that none of it ever feeds `sources`/`require`/`frameworks`/`libraries`/`executable`/`prefix` in this tree** — only `${dirname}`, `${dir}` and `${target}` do, and those three are resolved. |
| `files` / `copy` | line | yes (21× / 3×) | Resources/bundle asset copying (`files` runs the per-extension compiler transform first, e.g. `.xib`→`.nib`; `copy` doesn't). Recognised, not surfaced as inventory fields — out of scope for Task 1 (`--inventory` only; no `project.yml`). |

No directive outside this list was encountered anywhere in `Frameworks/`, `Applications/`,
or `vendor/`. The task brief's recon notes listed `resources` and `entitlements` as
directives; neither is actually a directive keyword in `bin/rave`'s grammar — `resources`
is a conventional glob-prefix and `files`/`copy` destination string, and `entitlements`
only appears inside `add CS_FLAGS "--entitlements '${CS_ENTITLEMENTS}'"` and as the
variable name in `expand CS_ENTITLEMENTS ...` (`Applications/TextMate`,
`Applications/mate`). Both are handled correctly as ordinary `add`/`expand` directives;
no dedicated `resources`/`entitlements` directive exists to implement.

## Target count: 57, not 56

`bin/rave2yaml --inventory` finds **57** targets across the 56 `Frameworks/*/default.rave`
+ `Applications/*/default.rave` files (46 + 10), plus 3 more in `vendor/*/default.rave`
(60 total). 57 ≠ 56 because `Frameworks/CommitWindow/default.rave` declares **two**
`target` blocks in one file — `CommitWindow` (the framework) and `CommitWindowTool` (a
helper executable it embeds via `files @CommitWindowTool "MacOS"`).

The test brief's original heuristic (`grep -l` — count *files* with a `sources`/
`executable` match) undercounts this by one, since `grep -l` counts a file once no matter
how many matching lines it has. `tests/rave2yaml_test.sh` was changed to count `target`
*directive occurrences* instead of matching files, which is exact (every target block
opens with exactly one `target` line, per `bin/rave`'s own grammar) and independent of
how many targets share a file. Confirmed correct, not tuned to fit: `declared` now
computes 57 by direct inspection of the `.rave` files, matching the parser.

The dependency-resolution check was also widened: `Applications/TextMate/default.rave`
`require`s `kvdb`, which is a `vendor/` target, not a `Frameworks`/`Applications` one. The
original test only accepted `^target ` names as valid; it now also accepts
`^vendor-target ` names, since vendor code is a real link/require target in the build
graph — it's just organizationally separate (see below), not exempt from dependency
resolution.

## Vendor targets, reported separately

Per plan: `vendor/*/default.rave` (`Onigmo`, `kvdb`, `xdiff`) is in scope for parsing but
tagged `vendor-target` rather than `target` in the inventory, since third-party code may
need different handling in the Xcode project (e.g. suppressed warnings, a different
target template, or exclusion from source-license scanning) than first-party code. They
remain valid `require` targets — `regexp` requires `Onigmo`, `scm` requires `xdiff`,
`TextMate`/`DocumentWindow` require `kvdb` — so dependency names resolve against the
union of `target` and `vendor-target` names, not `target` alone.

One non-obvious thing confirmed while building this: `vendor/kvdb/default.rave` writes
`sources vendor/kvdb/*.m`, which looks at first glance like a doubled path once joined
with the file's own directory (`vendor/kvdb` + `vendor/kvdb/*.m`). It isn't a bug —
`vendor/kvdb/` wraps a nested upstream checkout at `vendor/kvdb/vendor/`, whose own
internal layout is `vendor/kvdb/kvdb.h` etc. The doubled-looking path is real and
resolves to real files (verified: `vendor/kvdb/vendor/kvdb/kvdb.h`,
`vendor/kvdb/vendor/kvdb/kvdb.m`, `vendor/kvdb/vendor/kvdb/KVDBFunctions.m`).

## Out of scope for this task (not walked)

`PlugIns/dialog*/default.rave` (2 files: `PlugIns/dialog/default.rave` declares
`tm_dialog2` + `Dialog2`; `PlugIns/dialog-1.x/default.rave` declares `tm_dialog` +
`Dialog`) and the nested
`Applications/TextMate/support/Bundles/Bundle Support.tmbundle/src/default.rave` (target
`find_app`) exist but are not part of `Frameworks/*/default.rave` /
`Applications/*/default.rave` / `vendor/*/default.rave`, so `bin/rave2yaml` does not walk
them, matching the task brief's explicit walk instruction. **The two `PlugIns/dialog*`
files use only directives this tool already implements** (`target sources executable
frameworks add prefix files`) — they are out of scope purely because the walk scope
never included `PlugIns/`, not because of a grammar gap. Only the nested Bundle Support
file actually uses directives this tool doesn't implement (`arch`, `notarize`, `define`);
that's the one file in this group genuinely excluded for grammar-coverage reasons, not
just walk scope. `Applications/TextMate/default.rave`
embeds two of them by name (`copy @Dialog @Dialog2 "PlugIns"`) — Task 4 will need to
account for `Dialog`/`Dialog2` some other way, since they're invisible to this inventory.
Also out of scope: the root `default.rave` itself, which sets global flags applied to
every target (`C_FLAGS`, `CXX_FLAGS`, warnings, `-mmacosx-version-min`, a PCH prelude,
`libraries c++`, and a `debug`/`release` `config` block that adds `OakDebug` as a
dependency in debug builds) — none of that is per-target data, so Task 4 will need it
from `default.rave` directly, not from this inventory.
